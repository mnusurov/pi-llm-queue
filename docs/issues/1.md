# Issue 1: Spec: pi-llm-queue — serialise LLM access to protect KV-cache warmth

State: OPEN · Labels: ready-for-agent

## Problem Statement

The user runs local LLMs (llama.cpp, single constrained GPU, "strata" server at 192.168.1.100:8001) through pi. The server is not optimised for parallel sessions: when an orchestrator session interleaves model requests with subagent sessions (parallel subagent launches, async workflow children, multiple pi windows), every session switch evicts the KV cache slot and the next request re-prefills the entire context. Result: severe slowdowns, GPU thrash, and — for external providers (zen and other OpenAI-compatible APIs) — prompt-cache misses that cost real tokens.

## Solution

`pi-llm-queue`: a pi extension plus a single local daemon that serialises LLM access per model endpoint. The daemon grants a "slot" to a **session** (not a request) for a whole turn burst (turn-based affinity lease), so each session's append-only prefix stays cache-warm and context switches are rare and deliberate. Interactive parents get priority over subagent children with aging anti-starvation. Subagent launches are serialised by default on single-slot queues (orchestrator waits for the child's final answer). Providers on the same endpoint share one queue automatically (baseUrl keying); providers can be excluded or given higher `maxStreams`. Everything degrades fail-open if the daemon dies.

## User Stories

1. As a pi user on a local model, I want parallel sessions and subagents to stop evicting each other's KV cache, so that each turn continues warm without re-prefilling the whole context.
2. As a pi user, I want the orchestrator to wait for a subagent's final answer by default, so that the GPU serves exactly one session at a time on single-slot queues.
3. As an orchestrator, I want to launch a batch of subagents as one workflow call, so that I am woken once at the end and my large context is re-prefilled once, not N times.
4. As an orchestrator, I want parallel subagent launches to be arranged into a sequential queue, so that "parallel" in the prompt becomes "serial" on the GPU without me changing my workflow.
5. As an interactive user, I want my foreground session to outrank background subagents, so that the UI stays responsive while jobs run.
6. As a subagent, I want aging guarantees (boost after N parent grants or T seconds of waiting), so that I am never starved by a busy parent.
7. As a user running several interactive sessions, I want FIFO ordering within the parent tier, so that no window is privileged arbitrarily.
8. As a user with two provider entries on one GPU (strata + llamacpp), I want them to share one queue automatically, so that the endpoint is protected even without merging config entries.
9. As a power user, I want explicit resource groups in config, so that I can split one server into two queues (slots) or merge two endpoints behind one GPU.
10. As a user, I want to exclude a provider from queueing (`enabled: false`), so that free external APIs stay fully parallel when I choose.
11. As a cost-conscious user, I want external providers queued with `maxStreams > 1`, so that provider-side prompt caches stay warm and cache-miss token costs drop.
12. As a user, I want compaction and classifier calls to pass through the queue too, so that cache protection covers every model request of a session.
13. As a user pressing Esc, I want my queued request removed from the queue instantly, so that aborts feel immediate.
14. As a user, I want everything to keep working when the daemon dies (fail-open), so that the queue is never a single point of failure.
15. As a subagent runner, I want lease TTLs, so that a crashed session's slot is reclaimed automatically.
16. As a user, I want a live TUI indicator while my session waits for a slot, so that I know pi is queued, not hung.
17. As a user, I want a `/queue` status command, so that I can see the current slot holder, queue depth per tier, and session-switch counts.
18. As a power user, I want machine-readable JSON status, so that scripts can observe queue state.
19. As a developer, I want the daemon to auto-start from the extension, so that installation is a single `pi install`.
20. As a developer, I want the daemon to idle-exit after the last pi session disconnects (with a grace period), so that no orphan process lingers.
21. As a user, I want config hot-reload, so that policy changes take effect without restarting pi or the daemon.
22. As a user, I want `blockSubagentLaunch` configurable per queue, so that external multi-slot queues keep parallel launches while the GPU queue serialises them.
23. As a user without pi-subagents installed, I want the queue to work for plain sessions, so that there is zero hard dependency on any subagent extension.
24. As an integrator, I want a neutral `PI_QUEUE_ROLE` / `PI_QUEUE_GROUP` env contract, so that any runner (not only pi-subagents) can declare child roles and grouping.
25. As a user, I want a slash command to promote/demote my session's tier, so that I can override role detection ad hoc.
26. As a user, I want an optional `queueTimeoutMs` that degrades to fail-open with a warning, so that a stuck queue never hard-fails my run.
27. As a user, I want my slot held while long tool executions run (no model requests in flight), so that my session is not evicted mid-run.
28. As a user, I want a short grace period after my run settles, so that wake chains (parent woken by child) do not thrash the slot.
29. As a developer, I want the daemon's socket protocol documented, so that the whole scheduler is testable through one seam.
30. As a user, I want documented `httpIdleTimeoutMs` guidance (raise to ~900000), so that queue wait + long prefill do not trip pi's HTTP idle timeout.
31. As a future user, I want install and config docs, so that I can set this up on my own machine.
32. As a maintainer, I want scheduler behaviour verified through the daemon socket seam only, so that tests assert external grant order, not internals.

## Implementation Decisions

**Modules**

- **Daemon** (plain Node, zero deps, unix socket, JSON protocol): lease protocol `acquire(queueKey, sessionKey, role, group)` / `renew` / `release` / `status`; lease TTL with heartbeat; per-queue scheduler; idle-exit on zero clients after `daemonIdleExitMs` grace; config watcher for hot-reload.
- **Extension** (TypeScript, npm package `pi-llm-queue`): provider wrapper registered via `pi.registerProvider()` over configured providers, delegating to the built-in `openai-completions` stream after slot grant; per-session lease client keyed by session UUID (foreground children are separate sessions in the same process — leases are per-session, not per-process); daemon autostart (detached spawn + lockfile PID + stale reclaim); lease lifecycle driven by pi events (`agent_start` acquire, `agent_settled` release after grace, abort → immediate release); `tool_call` hook rewriting `subagent` `async:true→false` when `blockSubagentLaunch` is active for the target queue (soft integration: no-op when the tool is absent); `/queue` command; footer indicator; promote/demote slash override.

**Scheduling semantics**

- Queue key = provider `baseUrl`; explicit `queues.<name>.match` groups override; `enabled: false` → passthrough. Config keys accept provider names resolved to baseUrl; baseUrl entries win on collision.
- Slot granted per session, retained across the session's run (turn-based affinity); switch on release, idle quantum, or monopoly quantum (N requests / M seconds).
- Tiers: `parent` (interactive) > `child` (subagent); FIFO within tier; aging: boost longest-waiting child after `agingAfterSlots` consecutive parent grants or `agingAfterMs` waiting.
- Role resolution order: explicit `PI_QUEUE_ROLE` > `PI_SUBAGENT_CHILD`/`PI_SUBAGENT_PARENT_SESSION` hints (read as strings, no import — zero hard dependency on pi-subagents) > default `parent`.
- All model requests through the wrapper are queued: chat turns, tool loops, compaction, classifier calls, foreground children.
- `blockSubagentLaunch` defaults to `true` for queues with `maxStreams == 1`, `false` otherwise.
- Fail-open: daemon unreachable → requests pass through; `queueTimeoutMs` expiry → pass through with warning (no hard error); child default = unlimited queue wait.
- Grace after `agent_settled`: 2–5 s (wake chains), then slot released.

**Config** (`~/.pi/agent/llm-queue.json`, global-only, hot-reload)

```json
{
  "defaults": { "maxStreams": 1, "policy": "priority-aging", "agingAfterSlots": 3, "agingAfterMs": 60000, "failOpen": true, "daemonIdleExitMs": 60000 },
  "queues": {
    "http://192.168.1.100:8001/v1": { "maxStreams": 1, "blockSubagentLaunch": true },
    "zen": { "maxStreams": 3, "policy": "fifo", "blockSubagentLaunch": false }
  }
}
```

**Environment contract**: `PI_QUEUE_ROLE=child|parent`, `PI_QUEUE_GROUP=<id>` (set by our extension for processes it launches; readable by any orchestrator). Recommended pi setting: `httpIdleTimeoutMs: 900000`.

## Testing Decisions

- **Primary seam (covers ~90% of logic): daemon socket protocol.** Behaviour tests drive the unix socket with a test client simulating N sessions: grant order under FIFO, parent priority, aging anti-starvation, affinity retention across bursts, TTL reclaim of crashed leases, `maxStreams` enforcement, idle-exit, hot-reload, queueTimeout fail-open, abort removal. Assert external behaviour (who holds the slot, in what order, with what timing semantics) — never internal structures.
- **Secondary thin seam (pi glue): pi SDK session with a stub provider.** Abort propagation (Esc → queue removal), `blockSubagentLaunch` async rewrite, daemon autostart/lockfile.
- Greenfield repo: `node:test` + a plain socket client harness; no prior art to follow.
- E2E cache-warmth measurement against real llama.cpp is a separate human-validated ticket.

## Out of Scope

- `wakeBatching` (batched delivery of intermediate wake messages) — config stub only, feasibility unproven.
- TCP transport / multi-machine coordination (single machine only).
- Server-side proxy solutions (proxycache/Goldseam-style slot management).
- Per-model capacity pools and model-selection allocation.
- UI beyond the footer indicator; metrics dashboards; Windows support (unix socket).

## Further Notes

- Upstream validation: oh-my-pi issue #3812 documents the identical need ("subagents clobbering a parallel=1 llama.cpp backend"); vanilla pi has no subagent concept in core — subagent markers are extension-level, which is why the neutral `PI_QUEUE_ROLE` contract is the primary mechanism.
- pi facts used: `registerProvider` can replace a provider with a wrapper; `provider_stream_event` is notification-only (cannot gate requests), so the wrapper is the only reliable client-side interception point; `agent_start`/`agent_settled` give exact run boundaries for leases.
- Naming checked: `pi-llm-queue` free on npm (`llm-queue` is taken, unrelated).
